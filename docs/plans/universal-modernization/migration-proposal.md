## Necessary design corrections adopted from critique

Stable project ID, repository identity and runtime checkout/worktree binding are different. The proposed hash of project+repo was rejected as a physical-root verifier. Repository identity must not universally require GitHub owner/name; that syntax remains a host adapter constraint. Independent expectations come from controller registration/current host observation, not the record being verified.

Trusted approval sources include a bound explicit current user decision and designated policy refs, with scope, revision and supersession. Approval is not limited to main, nor inferred from a PR flag. Required merge evidence fails closed; unknown quota remains advisory.

Compatibility is directional: new code can explicitly read v1; old binaries are not promised to understand new records. Historical readable records need explicit binding before cross-project use. Preserve fingerprints/receipts/retries; do not silently remap absolute historical refs or delete state for rollback. Contract, schema, policy hash and distribution versions are separate.

Reject syntax-based subprocess bans, brittle documentation word-matching tests and a new state authority. Legitimate CLI/collector adapters may use subprocesses. Acceptances should test behavior, not mirror implementation.

## Choices and authorization boundary

Necessary: explicit identity/approval binding, arbitrary milestone support, defined shared invocation, version-aware legacy compatibility, one register and two-project acceptance before portability claims. Optional: thin entrypoint convenience, external state location, context-size/docs checks proportional to demonstrated drift. Deferred: package publishing/signing decisions, parallelism, real outage recovery, memory and efficiency benchmarks. Rejected: second scheduler, generic model upgrades, full-history dumps, private quota scraping, automatic state deletion and a monolithic Coordinator rewrite.

Before A1 implementation, approve its bounded scope and select the registration/approval-reference representation. Recommended default: a controller-owned envelope referencing the unchanged legacy binding, with a separately resolved checkout association; no derived physical-root hash and no operational state migration. External versus in-repo state and relocatable binding design can wait for C.

**Recommended next authorization:** A1 identity-binding adapter only. Expected owned components: one narrow controller binding helper, minimal Program/Delivery entry validation, focused tests and compatibility docs. Exact filenames/API are to be fixed in its bounded implementation plan. Acceptance: wrong project/repo/root and same-plan collisions fail; explicit current user approval works; PR-edited approval cannot self-authorize; immutable legacy bytes/receipts/retries survive; no dispatch occurs. No migration/adoption/merge is authorized by accepting this research output.
